## PFN-001：分时质量评估算分耗时与前端超时导致界面显示「-」但库中已有分

| 字段 | 内容 |
|------|------|
| **编号** | PFN-001 |
| **发现时间** | 2026-10-21（线上验证 600843·上工申贝·2026-10-21；关联 2026-10-17 分时质量模块首批测试与 001216 排查） |
| **模块** | `intraday-quality`（评估页批量/选中算分、Baostock 拉数） |
| **优先级** | 低（非致命；算分可落库，刷新列表可看到正确分数） |
| **问题现象** | 1. 点击「批量计算」后，按钮恢复可点，部分样本评分列仍为 **「-」**；重复计算仍可能为「-」。<br>2. **刷新评估列表**后，同一条样本显示正常数值（例：600843 为 **86.0**）。<br>3. 本机压测：Baostock **单次 login + 5m + logout** 偶发 **~60s**；同一会话内 5m/15m 查询约 **0.5～1s**，Wyckoff 算分约 **2s**（连上之后为秒级）。 |
| **问题原因** | 1. **前端**：`fetchAPI` 默认超时 **20s**（`frontend/packages/api/src/client.ts`），`/intraday-quality/compute` 未单独加长；Baostock 整段算分（含慢 login、多票 5m+15m）易 **>20s**，请求 abort 后 **不执行 `applyList`**，界面仍显示旧状态 `strength_score = null`。<br>2. **外部依赖**：Baostock 公网 **`bs.login()` / 首包** 偶发阻塞数十秒，属 **环境与接口稳定性**，非 Wyckoff 算分逻辑错误；后端仍可能在超时后继续算完并 **commit**。<br>3. **历史实现（已缓解）**：批量算分曾对每条样本 **login/logout**，放大登录慢的影响；现改为 **`BaostockSession` 批量共用一个登录**（`baostock_fetch.py` / `service.py`）。 |
| **解决方案** | **建议（未全部落地）**：<br>1. 为 `intradayQualityApi.compute()` 设置更大 `timeoutMs`（如 120000～180000），算分成功后再 `applyList`。<br>2. 超时提示改为：「请求超时，服务端可能仍在计算，请稍后刷新列表」；可选在失败行保留 `errors[].message`（评估页已有 `!` + title）。<br>3. 对 Baostock login/查询增加 **合理超时 + 有限重试**，避免无限挂起；失败写入 `errors`。<br>4. 中长期：分钟线 **按 symbol+date 缓存**；或 **异步算分任务** + 轮询/推送；降低对 Baostock 公网瞬时延迟的敏感度。<br>**已做缓解**：批量 `BaostockSession`、A 股代码补零、15m 失败时仍可用 5m 算分、算分失败 toast/行内提示（2026-10-17 前后）。 |
| **是否已解决** | **部分缓解**（批量单 session、失败信息展示）；**未完全解决**（前端 20s 超时与 Baostock login 偶发慢导致的 UI/库不一致、长耗时体验）。 |
